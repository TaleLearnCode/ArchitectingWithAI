# 04 — Architecture Documentation Prompts*Generate ADRs, process flows, specifications, and decision records — using templates.*---## Section PurposeDecisions made in Sections 1–3 must be recorded. Undocumented decisions are lost decisions.These prompts help you:- **Generate Architecture Decision Records (ADRs)** — capture *why* you chose an architecture, not just *what* you chose- **Create Process Flows** — document operational sequences, error handling, and decision points- **Build Architecture Specifications** — component responsibilities, interfaces, technology choices with rationale- **Record Risks & Assumptions** — everything you validated, everything that could go wrong- **Create runbooks and operational guidance** — so teams can actually run the architecture**Thesis Connection:** AI generates from constraints. Here it generates structured documentation that architects refine and approve.---## Prompt Catalog### Prompt Card 1: ADR Generation**Use This When**You've made a significant architecture decision and need to document *why* for future teams and stakeholders.**Prerequisites**- Architecture decision (e.g., "Use microservices instead of monolith")- Context that motivated the decision (constraints, business drivers)- Options considered (at least 2 alternatives)- Pros/cons specific to your project- Follow your team's ADR template format**Input Example**\\\DECISION: Use event-driven architecture for order processing instead of request-replyCONTEXT: High-volume order spikes during flash sales; need to decouple order intake from fulfillmentOPTIONS CONSIDERED:  1. Use **ADR Generation** with your decision + context + options   - Output: Structured ADR following your template   - Review: Architect refines context, options, consequences (AI output is a draft)2. **For each key process:**   - Use **Process Flow Generation** with process name + actors + steps   - Output: Numbered process with decision points, error handling, timing   - Review: Architect verifies sequence and adds timing reality (AI may oversimplify)3. **For the architecture as a whole:**   - Use **Architecture Specifications Generation** with component list + interfaces   - Output: Component diagram (text), responsibilities, technology choices with rationale   - Review: Architect verifies tech choices match constraints + team skills4. **For every risk surfaced in Section 3:**   - Use **Risk Register Entry Generation** with risk description + impact + current state   - Output: Entry with trigger, probability, impact, mitigation, contingency, monitoring   - Review: Architect estimates probability/impact (AI may be overly optimistic or pessimistic)5. **For every assumption made:**   - Use **Assumption Register Entry Generation** with assumption + rationale   - Output: Entry with validation plan, fallback plan, review cadence   - Review: Architect assigns owner and review date### Quick Documentation (30 minutes)- Generate 1–2 key ADRs (architecture choices, not every decision)- Generate process flows for user-facing paths (skip internal housekeeping initially)- Generate risk register entries for top 5 risks only### Comprehensive Documentation (2–3 hours)- Generate ADRs for all major architecture choices- Generate process flows for all user-facing + operational paths- Generate full Architecture Specification with component diagram- Generate risk register for all identified risks (Section 3 output)- Generate assumption register for all stated assumptions (Sections 1–3 output)---## Customization Guidance### By Audience- **Internal team:** ADRs + risk register sufficient. Lighter on architecture specification.- **Stakeholder review (CFO, CISO, CTO):** Emphasize ADR consequences and risk mitigation. Include architecture specification.- **New team members onboarding:** Add detailed process flows and operational runbooks.- **External audit (compliance, security):** Add assumption register with validation status and risk register with monitoring plan.### By Detail Level- **Lightweight (startup/MVP):** ADRs + risk register only. Skip specifications.- **Standard (product-stage):** ADRs + risk register + architecture specification + process flows for critical paths- **Comprehensive (enterprise/regulated):** All of the above + assumption register + operational runbooks + compliance mapping### By Template Adaptation- **Lightweight ADR:** Use 1-page template (decision, rationale, consequences only)- **Standard ADR:** Use 2-3 page template (decision, options, pros/cons, consequences, alternatives considered)- **Comprehensive ADR:** Use full template (decision, context, options, pros/cons, consequences, follow-up decisions, dependencies)---## Quality Checks### Before Using Generated Output- [ ] ADRs cite **specific constraints** that drove the decision (not vague reasoning like "this is scalable")- [ ] Process flows have **explicit error handling and decision points** (not just happy path)- [ ] Architecture specifications map each component to a constraint or requirement (e.g., "cache layer → <100ms latency SLA")- [ ] Risk entries include **specific monitoring strategy** (not "monitor for this risk" without saying how)- [ ] Assumption entries include **validation plan** with owner and date (not just "we assume
